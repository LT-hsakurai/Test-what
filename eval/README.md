# 検証ハーネス — 作り直しの前に決着させること

新しいアプリを1行も書く前に、**「偽検知の原因はアルゴリズムか、撮影条件か」**を数字で決着させるための道具です。

プロトタイプには評価データもテストも1件もありませんでした。そのため閾値崩壊バグ（異常度61870%）は実機で見るまで発覚せず、「精度が上がった」と主張するコミットにも裏づけがありませんでした。ここから始めるのはそのためです。

## 1. セットアップ

GPU のある PC で実行してください（CPU でも回りますが遅いです）。

```bash
python -m venv .venv
.venv\Scripts\activate        # Windows
pip install -r eval/requirements.txt
```

## 2. データを撮る

これが一番重要な工程です。**撮り方そのものが検証項目**（V4）になっています。

```
data/myproduct/
  train/    良品 10〜20枚   登録用
  good/     良品  10枚以上  評価用（train には入れない）
  ng/       不良   3枚以上  既知の欠陥
```

### train/ の撮り方 — ここを間違えると全部無意味になります

**連写しないでください。** プロトタイプは10枚を200ms間隔で撮っていました（実質2秒間・ほぼ同一画像）。その結果、良品の正常なばらつきが学習データに一切入らず、検査時に手持ちで動かした瞬間に閾値を超えていました。

正しい撮り方は**「置き直す → 撮る」を10〜20回**繰り返すことです。毎回、

- 製品をいったん持ち上げて置き直す
- 立ち位置と持ち方を少し変える
- 可能なら時間帯を変えて撮り足す（照明が変わる）
- 可能なら複数個体を撮る

**実運用で起きるばらつきを、意図的に学習データに入れる**のが目的です。

### V4 を測るなら

比較のために、同じ製品で `train_burst/`（従来どおり連写した10枚）も撮っておいてください。2つのデータセットで同じ設定を回せば、撮影方法だけの効果が分離できます。

### good/ と ng/

- `good/` は train と同じ撮り方で、**train には含めない**別の10枚以上（hold-out）
- `ng/` は既知の不良。傷・汚れ・欠けなど。**最低3枚**

`ng/` が無いと見逃し率も分離マージンも測れません。**NGサンプルを用意しないまま実運用に出したことが、プロトタイプ最大の失敗でした。**

## 3. 実行する

```bash
# フルフレーム（現行の再現を含む全設定）
python -m eval.run data/myproduct

# ROI を指定すると V6 も回る。x,y,w,h を 0-1 の相対座標で
python -m eval.run data/myproduct --roi 0.25,0.20,0.50,0.60

# 最重要の2つだけ先に見る
python -m eval.run data/myproduct --roi 0.25,0.20,0.50,0.60 --only baseline,V1b,V6a

# CSV に残す
python -m eval.run data/myproduct --csv results.csv
```

## 4. 何を見るか

| 指標 | 意味 |
|---|---|
| **偽NG率** | 良品を誤ってNGにした割合。現場の信用を最も損なう |
| **見逃し率** | 不良を OK と判定した割合 |
| **AUROC** | 閾値の決め方に依存しない、手法そのものの分離能力 |
| **分離マージン** | 正なら良品とNGが完全分離。**負ならどんな閾値を選んでも破綻する** |
| **良品CV** | 良品スコアのばらつき。大きいまま閾値を締めると必ず偽NGが出る |

**`baseline` と `V1b` と `V6a` の3行を比べれば、最重要の切り分けが終わります。**

- `V1b`（ぼかし除去）で大きく改善する → アルゴリズムの問題だった
- `V6a`（ROI）で大きく改善する → 背景を学習していたことが問題だった
- どちらでも改善しない → 撮影条件そのものを統制する必要がある（治具・照明）

## 5. 検証項目の対応

| 設定 | 何を検証するか |
|---|---|
| `baseline` | 現行 `backend/inspector.py` の再現 |
| `V1a` / `V1b` | ガウシアンぼかし σ=4.0 が異常マップを潰していないか |
| `V2a` / `V2b` | スコアの p99 が小面積の欠陥を無視していないか |
| `V3` | 入力 256×144 が傷の検出に不足していないか |
| `V4` | 連写登録 vs 置き直し登録（データセットを分けて実施） |
| `V5a`〜`V5c` | バンクのランダム間引きと、校正/推論のバンク不一致 |
| `V6a` / `V6b` | 背景を学習させることの害 |

## 6. 注意

このディレクトリは**検証専用**で、本番実装ではありません。`backend/` の現行コードには手を入れていないので、比較対象としてそのまま残っています。

`V6b` は最有力の組み合わせ（ROI + ぼかし除去 + 上位k平均 + coreset + 3×3プーリング）です。ここが baseline より明確に良ければ、v2 のコア設計はその方向で確定できます。
